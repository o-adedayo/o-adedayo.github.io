CASE-003 — Executive Impersonation (BEC) Phishing via Fabricated Reply Chain

1. Executive Summary

An employee at a managed client received an email that appeared to continue an existing conversation about one of the company's senior executives, sent by a display name of "Leadership Announcement." The user reported it as suspicious rather than replying. Header analysis showed the message came from a newly registered free consumer webmail account and that the "conversation" it claimed to continue never existed — the threading headers were fabricated by the sender. This is the standard opening move of a business email compromise campaign, which typically escalates to fraudulent payment, payroll, or gift card requests once the target engages. The message was purged, the sender blocked tenant-wide, and executive impersonation protection was added to the client's anti-phishing policy. No user interaction or compromise occurred.

2. Detection

  • An end user (operations-user-1) reported an unexpected external email with the subject [External] Re: [Executive Name], claiming to be a reply in a thread the user had no memory of.
  • The sender display name was "Leadership Announcement," but the underlying address was a free consumer webmail (Gmail) account with a throwaway naming pattern (personal name + trailing digit).
  • Escalated for full header analysis because the combination of an executive's name, a fabricated "Re:" subject, and an external free-mail sender matched a known BEC pretexting pattern — and the message had passed spam filtering (SCL 1) into the inbox.

Telemetry involved: Full SMTP message headers, Exchange Online Protection verdict headers, Microsoft Defender for Office 365 (Threat Explorer), message trace.

3. Triage & Scoping

The investigation centred on the raw header chain. The Received path confirmed the message genuinely originated from Google's mail infrastructure and relayed cleanly into the tenant's Exchange Online Protection frontends — ruling out transport-path forgery and focusing the analysis on sender intent. SPF passed, which is expected and non-exculpatory: authentication validates the sending domain's infrastructure, not the sender's legitimacy, and an attacker using a free webmail provider inherits that provider's passing SPF record.

The decisive finding was in the threading headers. The message carried In-Reply-To, References, and Thread-Index values implying an ongoing conversation, but both Message-IDs in the chain followed the same webmail-generated pattern from the same sender — the "original" message being replied to was authored by the attacker. The recipient never participated in any such thread. The payload was also packaged as application/ms-tnef (winmail.dat), an Outlook/Exchange-native format that is atypical for webmail-originated mail and obscures the body from casual inspection.

Scoping queries in Threat Explorer and message trace confirmed the sender had targeted only the single mailbox, and the recipient confirmed no reply or interaction. Severity was set at SEV-3: malicious delivery with no interaction or compromise.

4. Containment

The message was purged from the recipient's mailbox, and the sender address was added to the Microsoft Defender Tenant Allow/Block List to prevent redelivery. Blocking preceded any further analysis of the sender account because BEC openers are time-sensitive — the attacker's next step is a follow-up request, and cutting the channel immediately removes that opportunity. The user confirmed no reply had been sent, so no credential resets or session revocations were required.

5. Remediation & Recovery

The sample was submitted to Microsoft via the Submissions portal to improve upstream filtering. Recognizing that Gmail-based BEC actors rotate addresses cheaply, containment was not treated as sufficient: the impersonated executive was added to user impersonation protection in the client's Defender for Office 365 anti-phishing policy, so future display-name and lookalike impersonation attempts are flagged regardless of the sending address. The end user was briefed on the fabricated-thread technique and commended for reporting instead of replying.

6. Lessons Learned

What worked: User security awareness — the report came in fast and before any interaction. Header-level analysis identified the fabricated thread from a single content-light message, before the campaign could escalate to its financial phase.

What didn't: Content-based filtering scored the message SCL 1 and delivered it to the inbox. Text-only BEC openers with no links or attachments routinely evade content filters, and impersonation protection had not previously been configured for this executive.

What changed as a result: Executive impersonation protection was enabled in the anti-phishing policy, the sender was blocked tenant-wide, and the fabricated-reply-chain indicator (external free-mail sender + "Re:" subject + no matching sent item) was added to the triage playbook as a fast-classification heuristic.
