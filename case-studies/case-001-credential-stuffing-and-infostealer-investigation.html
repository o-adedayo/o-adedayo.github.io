1. Executive Summary

A SaaS Alerts notification flagged repeated Microsoft 365 authentication failures against a single managed client user account. Investigation confirmed an active, multi-day credential stuffing campaign — an attack where criminals use previously stolen username and password combinations to attempt automated logins at scale. The account had been targeted for approximately four weeks, with multiple password resets failing to stop the attacks because the root cause was never identified: the user's credentials were actively circulating in breach databases confirmed by seven Have I Been Pwned entries, including an active June 2026 stealer log, and being recaptured each time a new password was set. The endpoint was scanned with two independent tools and confirmed clean. The account was secured through session revocation, isolation, and a randomly generated password reset, with outstanding Conditional Access and MFA controls escalated to the client for immediate implementation.

2. Detection

How did this activity first surface?

  • SaaS Alerts platform fired an AzureActiveDirectory — IAM Event: Authentication Failure notification for username@[client].com within a filtered 30-hour window
  • The alert reported 6 events, all showing rotating source IPs with threat scores of 62–100 across known hosting and proxy ASNs
  • Applications targeted included Azure Active Directory Connect — a management-plane app with no business justification for a standard user at this organization, immediately flagging this as higher severity than the default Low rating assigned by the platform
  • Escalation trigger: error code 50076 (MFA Interrupt) was present in the data — this code fires only after a correct password is entered, meaning the attacker had already cleared the password barrier

Telemetry involved: SaaS Alerts AzureActiveDirectory event stream · Microsoft Entra ID sign-in logs · Have I Been Pwned · Microsoft Defender Offline scan · Malwarebytes scan

3. Triage & Scoping

Scoping questions asked

  • How long has this been happening? Answer: repeated password resets over ~4 weeks — none had been investigated beyond the reset itself
  • What applications are being targeted? Answer: not just Exchange / OfficeHome — Azure CLI, PowerShell, and Azure AD Connect were all present in the log
  • Has Conditional Access ever fired? Answer: no — every single attempt showed "Not Applied"
  • What devices does the user access M365 from? Answer: one work PC and one iPhone — confirmed directly with the user
  • Is there any evidence of a successful login? Answer: unknown — audit logging was not enabled on the tenant

Queries and pivots

The SaaS Alerts window was expanded beyond the 30-hour default to the full available range, revealing 40+ attempts over 4 days. This was the first significant pivot. Full sign-in logs were then exported.

Pivoted from error codes to IP reputation — all attacking IPs were cross-referenced against ASN ownership. Every IP resolved to known hosting or proxy-as-a-service providers (F.N.S. Holdings, GSL Networks, FranTech Solutions) with threat scores of 62–100, consistent with commercial botnet tooling.

Pivoted from the repeated reset pattern to breach intelligence — the affected email was checked against Have I Been Pwned to determine whether credentials were circulating in public databases.

Root cause identified: HIBP returned 7 confirmed data breaches, including a June 2026 Stealer Logs entry — confirming active infostealer malware had captured the user's credentials and exfiltrated them to Telegram-distributed stealer log databases. Every password reset performed over the prior four weeks was being captured and recirculated to attackers within days. Resetting the password without addressing the device was the reason all prior resets failed.

Evidence preserved

  • Full Entra ID sign-in log export (CSV) — 40+ records, 26–29 June
  • SaaS Alerts event export for the filtered alert window
  • HIBP breach report — 7 confirmed breaches, all including passwords
  • Defender Offline scan report — no threats detected
  • Malwarebytes scan report — no threats detected

Severity decision

Reclassified from Low (SaaS Alerts default) to SEV-1 Critical based on five factors: (1) error code 50076 confirming a valid password was held by the attacker; (2) Azure management plane app targeting indicating privilege escalation intent; (3) confirmed presence in an active June 2026 stealer log; (4) zero Conditional Access controls on the tenant; (5) four-week dwell with three prior failed resets indicating unresolved, persistent credential access.

4. Containment

Actions taken — in execution order

1 · Revoke all active M365 sessions

All active refresh tokens were invalidated immediately. This terminates any authenticated sessions in progress — including any session cookies a stealer may have already exfiltrated — without requiring a password reset first. 

Connect-MgGraph -Scopes 'User.ReadWrite.All'
Revoke-MgUserSignInSession -UserId 'finance-user-1@[client].com'

2 · Block sign-in (account disable)

Sign-in was blocked before the password reset. Resetting the password while the endpoint might still be infected would immediately hand the new credential to the malware. 

Update-MgUser -UserId 'finance-user-1@[client].com' -AccountEnabled:$false

# Verify
Get-MgUser -UserId 'finance-user-1@[client].com' -Property AccountEnabled | Select-Object AccountEnabled

3 · Isolate endpoint

The work PC was disconnected from Wi-Fi and ethernet before any further action, preventing any active stealer from exfiltrating a newly set password and stopping C2 communications during scanning.

Decision rationale — why in this order: Session revocation before password reset is the correct sequence because active session tokens are independent of the password — an attacker with a stolen session cookie stays authenticated even after a password change. Account disable before endpoint scan ensures no new credentials can be captured by active malware during the investigation window.

Deliberate hold: The password was not reset until after both endpoint scans completed. This is why four weeks of prior resets failed — the credential was being captured before the account was ever secured.

5. Remediation & Recovery

Endpoint investigation

  • Microsoft Defender Offline Scan — pre-boot scan run on the isolated device. Result: No threats detected
  • Malwarebytes full scan — second-opinion scanner known to catch infostealer families (Redline, Lumma, Vidar) that Defender can miss. Result: No threats detected
  • Installed software review — checked for unknown RATs, cracked software, unofficial extensions, and recent unknown installs. Result: Nothing suspicious found
  • Device scope confirmed — user confirmed work PC (scanned) and iPhone only. No other devices in scope.

Password reset

A randomly generated 24-character password was applied. The password was not disclosed to the user — stored in the RMM only. This prevents reuse of any previously breached credential and eliminates social engineering disclosure as a vector. 

Add-Type -AssemblyName "System.Web"
$password = [System.Web.Security.Membership]::GeneratePassword(24, 6)

$params = @{
    passwordProfile = @{
        forceChangePasswordNextSignIn = $false
        password = $password
    }
}
Update-MgUser -UserId 'finance-user-1@[client].com' -BodyParameter $params

# Re-enable account after remediation
Update-MgUser -UserId 'finance-user-1@[client].com' -AccountEnabled:$true

6. Lessons Learned

What worked:

  • Expanding the log window beyond the SaaS Alerts default (30 hrs → 4 days) revealed the true attack scale — 40+ attempts vs. 6
  • Error code analysis was the pivotal step — 50076 alone elevated this from routine spray to confirmed credential compromise and directed the entire response
  • Using HIBP as a threat intelligence source explained a four-week mystery in minutes; no amount of sign-in log analysis alone would have surfaced that credentials were actively circulating in breach databases
  • Two-scanner approach (Defender Offline + Malwarebytes) gave higher confidence in the clean result than a single tool
  • Sequencing containment correctly — revoke sessions → disable account → scan endpoint → reset password — broke the capture-and-reuse loop that had been running for weeks

What didn't work / gaps identified:

  • Audit logging was not enabled on the tenant — it was impossible to confirm or rule out successful logins, mailbox rule changes, or OAuth grants during the four-week dwell period
  • SaaS Alerts' default Low classification for 50076 events delayed escalation — the platform's out-of-box rules do not treat MFA interrupt as high severity
  • Four weeks of repeated password resets with no root cause investigation — prior resets treated the symptom, not the cause; a triage checklist for repeat reset tickets should exist
  • No Conditional Access baseline on the tenant — the entire attack was viable solely because MFA was never enforced

What changed as a result:

  • SaaS Alerts alert rules updated: error code 50076 escalated to Critical across all managed tenants
  • Conditional Access baseline policy deployment added to client onboarding checklist
  • Microsoft Purview audit logging enabled on the affected tenant immediately post-incident
  • Repeat password reset ticket workflow updated: HIBP check and sign-in log review now mandatory on second reset within 30 days
